❯ why this venv, why is it there?                                               

⏺ venv is a Python virtual environment, an isolated folder with its own Python
  interpreter and its own installed packages. It's there so this project's
  dependencies (Flask 3.1.3, Werkzeug 3.1.6, pytest and so on) stay separate
  from your system Python and your other projects. Without it, installing a
  package for one project could break another that needs a different version.

  - How it got there: someone (probably you, or the course setup) ran python3 -m
    venv venv and then pip install -r requirements.txt. The folder is dated Oct
    2, the same day as the project files.
  - Git: it's listed in .gitignore, so it isn't committed. It's large and
    specific to your machine, and anyone else can rebuild it from
    requirements.txt.
  - Safe to delete? Yes. If it breaks, delete it and recreate it:
  rm -rf venv
  python3 -m venv venv
  source venv/bin/activate
  pip install -r requirements.txt

  source venv/bin/activate makes python and pip in your terminal point at that
  environment. deactivate turns it off again.

❯ is it a general practice to do this?                                          

⏺ Yes, it's standard practice in Python. Almost every project, from small
  scripts to production apps, uses one virtual environment per project.

  - Why it's the norm: different projects need different package versions, and
    installing everything globally causes conflicts. Newer macOS and Linux
    Python installs also block global pip install by default (the "externally
    managed environment" error), which pushes you toward venvs.
  - Reproducibility: a venv plus requirements.txt lets anyone get the same setup
    with one command.
  - Common conventions:
    - Name the folder venv or .venv.
    - Add it to .gitignore, as your project does.
    - Commit requirements.txt, not the venv itself.
  - Alternatives: tools like uv, poetry, pipenv and conda do the same job with
    extra features. uv is increasingly popular because it's much faster, but
    they all follow the same idea of isolating each project's packages.

❯ venv/bin/activate                                                             

⏺ Running venv/bin/activate on its own won't work. It's a shell script that has
  to be loaded into your current shell, so you need source in front of it:

  source venv/bin/activate

  Without source, you'll get "permission denied" because the file isn't
  executable. Even if it ran, it would run in a subshell and the activation
  would be lost when it exited.

  When it works, your prompt gets a (venv) prefix. After that, python app.py
  uses the venv's Python and Flask. Type deactivate to leave the environment.
